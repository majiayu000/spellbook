# Skill Layering Architecture

Spellbook should support reusable skill variants without requiring forks to copy
whole skill directories. This document proposes a layering model for core
skills, capability extensions, organization presets, local overrides, and
generated adapters.

The design follows the Spellbook operating contract: local inspection and draft
generation can run directly, while publishing, destructive changes, credential
handling, and high-context file edits require explicit escalation.

## Goals

- Let teams customize behavior without editing upstream core skills.
- Make local changes distinguishable from upstream content.
- Track installed/generated content so update and uninstall behavior is clear.
- Express runtime compatibility, required tools, and side-effect boundaries in
  metadata.
- Keep validation deterministic and network-free for the first implementation.

## Definitions

| Term | Meaning |
|---|---|
| Core skill | A skill shipped in `skills/<name>/SKILL.md` or `skills/<name>.SKILL.md` and tracked by the Spellbook registry. |
| Extension or capability pack | A package that adds new skills, scripts, assets, templates, agents, or references without changing an existing core skill by default. |
| Preset or override pack | A package that changes how existing skills behave for a team, organization, runtime, or policy set. |
| Local override | A user-owned layer outside the repository or in an ignored local directory. It has the highest priority and must never be overwritten silently. |
| Generated adapter | A generated runtime-specific wrapper, command, manifest, or compatibility file derived from core skills plus layers. |

## Layer Order

Resolution is deterministic. Higher layers override lower layers only through a
declared composition strategy.

1. Local override
2. Preset or organization policy
3. Extension or capability pack
4. Core Spellbook skill

Default behavior is conservative:

- Core skills are immutable input during resolution.
- Extensions add capabilities unless they explicitly target an existing skill.
- Presets may modify existing behavior only through a manifest entry.
- Local overrides win, but they are reported as local state and are never pruned
  without user confirmation.

## Proposed Directory Layout

```text
skills/
  <core-skill>/SKILL.md
  <core-skill>/references/...

layers/
  extensions/
    <extension-id>/
      manifest.json
      skills/
      scripts/
      assets/
      templates/
      agents/
  presets/
    <preset-id>/
      manifest.json
      overrides/
      references/
      templates/

.spellbook/
  install-manifest.json
  generated/
    <runtime>/
      skills/
      agents/
      commands/
```

Local overrides should live outside committed source by default, for example:

```text
$XDG_CONFIG_HOME/spellbook/overrides/
  manifest.json
  overrides/
```

When `XDG_CONFIG_HOME` is unset, the fallback is
`~/.config/spellbook/overrides/`. Local overrides must not live under the
managed Spellbook checkout, such as `~/.spellbook`, because install and
uninstall commands may update or remove that checkout.

Committed `layers/` content can be validated in CI. Local override directories
are validated before install but are not committed or generated by default.

## Manifest Schema

Each layer has a manifest with stable IDs and explicit effects.

```json
{
  "id": "org-review-policy",
  "version": "0.1.0",
  "type": "preset",
  "compatibility": {
    "spellbook": ">=0.1.0",
    "skills": {
      "threads": ">=0.1.0"
    }
  },
  "runtime_targets": ["codex", "claude"],
  "effect": "read-write",
  "required_tools": ["git", "gh"],
  "provides": {
    "skills": [],
    "scripts": ["scripts/review_gate.py"],
    "assets": [],
    "templates": ["templates/review-checklist.md"]
  },
  "applies": [
    {
      "target": "skills/threads/SKILL.md",
      "strategy": "append",
      "source": "overrides/threads-review-policy.md"
    }
  ]
}
```

Required metadata fields:

| Field | Required | Purpose |
|---|---|---|
| `id` | yes | Stable layer ID. Lowercase kebab-case. |
| `version` | yes | Layer version used by install manifests and rollback. |
| `type` | yes | `extension`, `preset`, `local-override`, or `generated-adapter`. |
| `compatibility` | yes | Spellbook and optional per-skill version constraints. |
| `runtime_targets` | yes | Runtime names such as `codex`, `claude`, or `all`, aligned with `install.sh --target`. |
| `effect` | yes | `read-only`, `read-write`, or `remote-write`. |
| `required_tools` | no | Commands or MCP capabilities required by the layer. |
| `provides` | yes | Files made available by the layer. |
| `applies` | no | Explicit modifications to lower-priority content. |

Effect semantics:

- `read-only`: adds instructions or metadata only.
- `read-write`: may generate or install local files.
- `remote-write`: may publish, push, comment, merge, deploy, or call remote write
  APIs. This requires explicit user approval before execution unless the current
  workflow already grants it.

## Composition Strategies

| Strategy | Behavior | Use |
|---|---|---|
| `replace` | Higher layer fully replaces the target artifact. | Local emergency override or runtime-specific adapter. |
| `prepend` | Higher layer content appears before lower layer content. | Stronger policy that must be seen first. |
| `append` | Higher layer content appears after lower layer content. | Additional checks, examples, or references. |
| `wrap` | Higher layer provides a wrapper template with an explicit insertion marker for lower layer content. | Runtime adapter or controlled policy envelope. |

`wrap` requires exactly one insertion marker:

```text
<!-- spellbook:base-content -->
```

If a strategy is missing, resolution fails. Silent implicit replacement is not
allowed.

## Resolution Algorithm

1. Discover core skills from `skills/` and registry metadata.
2. Load extension manifests, then preset manifests, then local override
   manifests.
3. Validate every layer before composition:
   - manifest fields are present and typed correctly
   - IDs are kebab-case and unique
   - layer-owned paths such as `provides` entries and `applies.source` stay
     inside the layer directory
   - `applies.target` paths are relative Spellbook artifact paths and resolve
     only to known core or generated targets
   - referenced files exist
   - runtime targets are known
   - required tools are declared
   - `effect` is compatible with the requested install mode
4. Build a layer graph keyed by target artifact path.
5. Compose each target from the lowest-priority base upward: core content first,
   then extensions, presets, and finally local overrides. This keeps the
   highest-priority layer outermost for `prepend`, `append`, `replace`, and
   `wrap`.
6. Write generated adapters into `.spellbook/generated/<runtime>/`.
7. Write or update `.spellbook/install-manifest.json`.
8. Install generated or source artifacts into runtime-specific locations.

The resolver must produce a concise report:

```text
resolved:
- target:
  base:
  layers:
  strategy:
  output:
  effect:
  warnings:
```

## Install Manifest

The install manifest records what Spellbook owns. It is the source of truth for
safe update and uninstall.

```json
{
  "schema_version": 1,
  "runtime": "codex",
  "installed_at": "2026-01-01T00:00:00Z",
  "source_ref": "main@<commit>",
  "layers": [
    {"id": "github-queue", "version": "0.1.0", "type": "extension"},
    {"id": "org-review-policy", "version": "0.1.0", "type": "preset"}
  ],
  "artifacts": [
    {
      "path": "~/.agents/skills/threads/SKILL.md",
      "source": ".spellbook/generated/codex/skills/threads/SKILL.md",
      "owner": "spellbook",
      "target": "skills/threads/SKILL.md",
      "layers": ["org-review-policy"]
    }
  ]
}
```

Uninstall behavior:

- Remove only artifacts owned by the manifest.
- Restore a lower-priority artifact if the removed layer had replaced it.
- Leave user-owned local overrides untouched.
- Refuse to delete or rewrite high-context files unless the user explicitly
  approves the exact path.

High-context files include `AGENTS.md`, `CLAUDE.md`, runtime settings, hooks,
shell profiles, credential files, and generated CI secrets.

## Validation

Layer validation should extend the existing registry and artifact checks:

- registry consistency for core skills and layer-provided skills
- missing file detection for `provides` and `applies`
- path containment for layer-owned paths, plus separate validation that
  `applies.target` names a known Spellbook artifact
- duplicate skill names across resolved layers
- unresolved placeholders in generated adapters
- compatibility checks for Spellbook version, runtime target, and declared skill
  versions
- effect checks so `remote-write` layers cannot run in read-only mode
- install-manifest drift detection

Validation remains local and deterministic in the first implementation. Network
checks can be added later as explicit opt-in audit steps.

Per-skill version constraints require a version source before they can be
strictly enforced. The first implementation should read an optional `version`
frontmatter field or registry version when present. If a manifest declares a
constraint for a skill that has no version yet, validation should report an
advisory warning instead of rejecting the layer. Strict per-skill version
rejection should wait until core skills publish versions consistently.

## Worked Example: Policy Preset

An organization wants stricter review behavior for the `threads` skill.

```text
layers/presets/org-review-policy/
  manifest.json
  overrides/threads-review-policy.md
  templates/review-checklist.md
```

`manifest.json`:

```json
{
  "id": "org-review-policy",
  "version": "0.1.0",
  "type": "preset",
  "compatibility": {"spellbook": ">=0.1.0", "skills": {"threads": ">=0.1.0"}},
  "runtime_targets": ["codex"],
  "effect": "read-write",
  "required_tools": ["git"],
  "provides": {
    "skills": [],
    "scripts": [],
    "assets": [],
    "templates": ["templates/review-checklist.md"]
  },
  "applies": [
    {
      "target": "skills/threads/SKILL.md",
      "strategy": "append",
      "source": "overrides/threads-review-policy.md"
    }
  ]
}
```

Result: generated `threads/SKILL.md` keeps the upstream core content and appends
the organization review policy. The install manifest records that the installed
artifact is composed from core `threads` plus `org-review-policy`.

## Worked Example: Capability Extension

A team wants a GitHub queue pack that adds a reviewer checklist, a queue
template, and a helper script without changing existing skills by default.

```text
layers/extensions/github-queue/
  manifest.json
  skills/github-queue/SKILL.md
  scripts/queue_summary.py
  templates/pr-review-checklist.md
```

`manifest.json`:

```json
{
  "id": "github-queue",
  "version": "0.1.0",
  "type": "extension",
  "compatibility": {"spellbook": ">=0.1.0"},
  "runtime_targets": ["codex", "claude"],
  "effect": "remote-write",
  "required_tools": ["git", "gh"],
  "provides": {
    "skills": ["skills/github-queue/SKILL.md"],
    "scripts": ["scripts/queue_summary.py"],
    "assets": [],
    "templates": ["templates/pr-review-checklist.md"]
  },
  "applies": []
}
```

Result: the extension installs a new `github-queue` skill and helper files. Since
the effect is `remote-write`, workflows using it must confirm authorization
before writing comments, pushing branches, merging PRs, or closing issues.

## First Implementation Scope

Build the smallest manual workflow first:

1. Manifest parser for committed `layers/extensions/*/manifest.json` and
   `layers/presets/*/manifest.json`.
2. Local validation command that reports layer errors without installing.
3. Resolver that can compose markdown artifacts with `replace`, `prepend`,
   `append`, and `wrap`.
4. Generated output under `.spellbook/generated/<runtime>/`.
5. Install manifest write/update for generated artifacts.
6. Unit tests with malformed fixture layers.

## Out Of Scope

- Migrating existing skills into layers.
- Scheduled synchronization or background automation.
- Remote marketplace publishing.
- Network-dependent compatibility checks.
- Automatic modification of high-context files.
- Secret management or credential provisioning.
- Merge or release automation for layer updates.

## Follow-Up Implementation Issues

- Add `scripts/validate_layers.py` for manifest schema, path containment,
  duplicate names, and compatibility checks.
- Add optional `version` frontmatter or registry versions to core skills before
  enforcing strict per-skill compatibility constraints.
- Add a resolver library with tests for `replace`, `prepend`, `append`, and
  `wrap`.
- Add installer support for generated `.spellbook/generated/<runtime>/` output
  and manifest-owned uninstall.
- Add documentation for local override setup and recovery.
- Add migration guidance for turning copied organization skills into presets.
