# Blender 执行与版本可靠性

这些规则适用于脚本构建、自动取景和已有工程修复。它们验证执行与产物身份，不证明造型相似。

## 构建失败不能进入后续渲染

Blender Python 抛异常时，默认进程退出码可能仍为零；旧 `.blend` 留在原路径，后续渲染便会生成貌似成功的旧结果。曲线坐标解包等构建错误也必须中止后续阶段。

- 在 `--python` 前传入 `--python-exit-code 1`，调用端使用 `subprocess.run(..., check=True)` 或等价失败中止机制。构建失败后停止依赖它的渲染、检查和完成报告。
- 保存分阶段日志，核对本轮预期部件或属性，再从实际保存文件重开检查。输出路径存在、文件时间或返回码不能单独证明新改动已生成。
- 多阶段或容易混淆版本的构建，记录输入、脚本、工程和渲染的版本/哈希。只读验收不要顺手重写源工程。哈希用于关联证据，不作相似度评分。
- 生成脚本、内嵌脚本和重现说明应对应交付版本。局部修补后的模型若仍保留旧生成器，明确“基线构建 + 修补”的顺序，避免重跑恢复已删除部件。

## 批量变形与附属几何

网格顶点坐标是三维；曲线 Poly/NURBS 点的 `co` 含第四维权重。几何计算取前三维，写回保留第四维；Bezier 点按其实际类型处理。不要让同一坐标解包假设覆盖所有对象。

发束与其描边、高光条等附属几何使用一致的形变和坐标空间；表面投射失败应记录对象与命中状态并修正目标或方向，不能用任意深度悄悄代替。限定变形对象集合，避免影响相机、灯光或不相关部件。

## 比较相机与展示取景

配准相机用于前后对照，保持投影、画幅和尺度。新增长发超出展示画面时，可以单独调整展示相机，不能把重新取景当作几何改善。

自动取景曾受空对象的 `bound_box` 哨兵值影响，导致模型异常缩小；有限数值检查发现不了这种错误。对待展示几何取依赖图求值结果，必要时用 `evaluated_object.to_mesh()` 获取实际顶点，跳过空结果，并在读取后 `to_mesh_clear()`。将顶点从对象空间变换到世界空间，再到相机空间；正交取景同时考虑宽高、画幅比例、中心与余量。透视相机需按其投影计算，不能套用正交尺度。

最终看图确认既无裁切，也没有过量留白。仅断言全部顶点在画幅内，会放过模型缩得过小的问题。

## 灰模与诊断隔离

使用独立检查场景、材质覆盖和灯光数据，避免修改共享灯光影响正式渲染。重复执行时设置明确能量，不要每次在现有能量上再乘系数。保持前后灰模相机与照明一致；脸部隐藏头发，头发另做去纹理检查。

## 保留用户状态与最小修改

修改已有工程前核对当前磁盘文件与 UI 状态：文件名、未保存标记、用户刚完成的保存都可能改变有效输入。存在未保存修改时先保留可恢复副本；无法安全取得时说明具体缺口，不以旧磁盘版本覆盖。UI 状态变化后重新读取，后台与 UI 不并发保存同一文件。用户切到新场景后，不为展示结果强行重新打开旧工程。

UI 粘贴超时不等于未输入，先检查界面再决定重试或提交，避免执行两遍。

用户要求去掉脖子时，先判断它是否独立对象。独立对象可在新版本中删除并解除所有场景链接；融合网格需要局部切除与必要封口。先检查头壳是否已闭合，已有封闭头壳无需重新塑形。重开后验证实际不存在，不能只隐藏渲染。

对需要保持的脸型或其他对象，在相同拓扑与顶点顺序下可比较坐标或哈希；拓扑改变时改用对应空间的轮廓/曲面比较。坐标一致仅证明坐标未改，若声明外观不变，还应按改动风险核对对象变换、修改器、材质和可见性。若去颈检查只覆盖其余网格与曲线坐标，就不能将其扩大解释为所有状态完全相同。

## 露色和穿插：从可见像素定位几何

连续调整透明度或整体缩放仍不能消除缺口时，改用定位诊断：

1. 从出现问题的固定相机、画幅和像素建立射线。正交相机改变射线起点，透视相机改变方向；核对画面纵轴和相机坐标变换。
2. 对候选对象取依赖图求值网格，在统一世界空间求交，按距离列出对象、面、位置和材质。近处透明发片不一定是最终可见表面，不能只看第一个几何命中。
3. 检查命中处 UV 和 alpha。精确采样需要插值命中点 UV；面的平均 UV 只能辅助定位。检查帧边、贴图边界和求值后的厚度，区分 UV 越界、透明孔洞、头壳穿出及后发抢到前层。
4. 修实际责任对象：例如仅加宽内层发根的局部覆盖。同步检查原视角和邻近视角，防止“侧面补缝”变成正面额前帽沿或锯齿边。

这类射线诊断定位遮挡，不是相似度或全局无自交证明。及时释放临时求值网格，诊断不保存回制作工程。

环绕或镜像参数化生成的曲面出现中线直缝时，除 UV 和 alpha，还应核对参数在中线及周期接缝两侧的连续性；留意绝对值折返等操作是否让相邻边界分离。修正后用原缺陷位置及两侧的同位置射线与固定视角渲染复查覆盖。

## 缩短迭代，同时保持证据对应

- 局部修正先渲染问题视角及可能受影响的邻近视角，方法稳定后再输出交付多视图。不要每改一个参数就重建整套图，也不要靠反复轮询日志代替看图。
- 实质改动前保留对应的关键视图、参数或检查点；同名日志和输出会覆盖历史，报告应区分实际保留的证据和对话中的观察。
- 构建异常中止后续渲染和验证；构建成功后再执行依赖它的检查。检查结果、比较拼图和最终文件应属于同一版本，不能混用旧图填补新轮次缺失。
- 若最后仅保存了 UI 布局，更新文件哈希并做与变化相称的重开检查；无几何或材质变化时，不必因此重复全部渲染。

### 及时反馈与中断恢复

- 将一次试验控制在“明确差异 → 一次有依据的修改 → 少量关键视图 → 看图决定”的闭环内。持续工作时至少每分钟给出简短进展，说明已获得的证据及下一步，不把多个后台阶段串成长期无反馈的等待。
- 渲染耗时、工具返回耗时和图像检查状态分别记录。用户问为何卡住时，先核对该任务日志与进程；渲染已退出就说明已退出，不能把后续延迟都归因于电脑性能，也不能凭猜测解释整段耗时。
- 一次读取过多图片或日志导致截断时，缩小输出，逐张检查尚未看到的图片。已有成功输出不必重渲染；尚未看到的图不能记录为已目视验收。
- 中断后检查原进程句柄、日志和产物，再决定继续观察或修复；观察超时不等于进程终止。多个 Blender 任务并行存在时，用具体命令、输入输出路径识别当前任务，不凭进程名停止其他任务。
- `open_mainfile` 后重新按已保存的名称取得对象、场景和材质；打开前持有的 Blender RNA 引用已经失效，不能再从旧对象读取名称来做检查。

## UI 恢复副本与展示状态

需要展示新工程而旧 UI 有未保存修改时，可以先用 Blender 的保存副本功能（如 `save_as_mainfile(copy=True)`）写入不冲突的新路径，确认副本有效且原文件路径未被替换，再打开新版本。打开前重新核对 UI，用户若已切换场景，不强行跳回。

展示时根据当前任务使用场景灯光/世界设置，避免材质预览的默认灯光造成与交付渲染不同的肤色；辅助线可关闭以便观察。UI 干净、文件能打开和渲染质量是不同检查。
