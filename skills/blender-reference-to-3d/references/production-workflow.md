# 人物制作与验收流程

## 1. 输入与目标

新角色建模先执行 [技能入口中的九视图流程](../SKILL.md)：水平 8 方向加正上方，默认不含正下方；完成生成和检查后再进入下方配准与制作。已有合格参考复用，局部修模不重复生成。

建立简短任务记录：目标人物、主参考、制作范围、静态/动画/打印等用途、需要保留的对象、期望交付格式。阶段标准取决于用途，不预设所有人物都需要绑定或水密网格。

对参考分类：原始图、用户批准的图、生成补图、人工推断。视图名称为“正面/侧面”不代表相机已知或几何一致。比较眼线、鼻底、嘴线、下巴和头顶在不同图中的关系；冲突时先选主参考，将其余视图作为风格或体积约束。影响人物身份的冲突需要用户选择，普通隐藏区域可合理补全并记录。

留存原图，配准副本记录裁切及等比缩放。比较图不能为追求吻合而单独拉伸渲染。可以生成补图帮助讨论，但新增视图尚需几何一致性检查。

## 2. 基线与工具

检查可用 Blender 可执行文件、版本、插件/连接状态和既有工程。读取旧脚本的输入依赖与写出路径再运行，避免覆盖手工版本。背景进程写入的文件不要同时在 UI 保存。

推荐按项目需要设置：原始参考目录、导入资源、制作脚本、版本工程、渲染和检查报告。为每次实质迭代记录输入版本、改动目标、固定相机、输出路径及观察结果。不要仅保存最后一张漂亮截图。

模板适配应检查眼口边流、头部体积、UV、材质及目标用途。程序化基本体可用于比例草模；需要精细人脸时，根据失败部位使用模板变形、局部重拓扑或雕刻。参数化方法本身不是禁用项，但需要有适合目标风格的表示和反馈。

准确记录实际方法：人工估计截面、手写深度场和参考投射不能称为训练模型推理或自动多视图优化。真人重建方法是否适合二次元，应检查其形状先验和实际输出；不能仅因使用了人脸模板就声称应用了某个重建算法。

## 3. 相机与粗形

先设定统一坐标轴、单位、画幅和参考板。正面与侧面配准时先对齐可识别标志，记录投影方式和参数。正交相机适合近似正交设定；摄影或明显透视插画需考虑焦距与透视。不要借修改头部去抵消相机错误。

先观察头颅、颧颊、下颌、下巴和五官间距。在灰模下比较正面、侧面、约 30–45° 斜侧面；只有存在可配准的对应原图时，斜侧面才用于定量对照，否则用于检查曲面连续性、体积和遮挡。

低密度阶段解决比例。细分提高光滑度，不自动改善脸型。保留修改前后同相机渲染，检查一个视角变好时是否破坏其他视角。

修复鼻口深凹和尖下巴时，同时检查正面下颌宽度，避免把“连续、柔和”做成圆胖脸。必要时分别控制下脸宽度与中央侧面深度，并核对耳部位置。保留纠正后的基线，后续头发修改不应顺带改变脸型。截面头壳可作为静态修形的一种表示，动画用途仍需独立验证拓扑与形变。

灰模有条带或折痕时，先区分真实曲面、法线和材质问题。若已平滑、无自定义法线且共边绕序一致时仍有条带，应检查低频形体、顶点布局和变形过渡，而非反复开启平滑或增加细分。

## 4. 完整脸部

| 部位 | 需要检查的关系 | 典型失败表现 |
|---|---|---|
| 眼部 | 眼面/眼球深度、上下眼睑厚度、眼角闭合、眉睫贴合 | 浮在脸上的贴片、眼睑缝隙、转侧后塌陷 |
| 眉毛 | 弧度、眉头眉尾收尖、中段粗细，以及与刘海的遮挡 | 等宽粗线、悬浮、几何眉线与头发纹理中的眉线重影 |
| 鼻部 | 鼻根到鼻尖与鼻底的体积过渡 | 正面像原图但侧面为平板或尖刺 |
| 嘴部 | 唇缝、口角、上下唇与口周连接 | 线条悬浮、端点重合退化、闭嘴仍露缝 |
| 下颌 | 颊部向下巴的连续过渡；包含脖子时再检查衔接 | 正面变宽、折痕、锯齿、穿插或可见开口 |
| 耳部 | 耳根贴合、耳缘、凹入耳窝、耳垂和侧向厚度 | 仅椭球或正面贴片、耳窝反凸、与头部悬空 |

风格化眼面可以满足静态展示，但不能因此宣称具有可转动眼球或闭眼能力。若需动画，加入与风格一致的视线、眼睑变形及口腔结构，并测试实际形变。

修改表面后检查眉睫、眼睑、嘴唇等附属件是否仍贴合。在不同视角检查，不能只把它们沿单一相机方向推到前面。

程序化制作时优先让眼面、睑沿和眉睫引用同一最终脸面函数或投射目标，避免各自使用过期深度。换掉低清眼部贴图时，盘点其中烘焙的眼线、睫毛和眼角，将仍需要的部分显式重建；检查眼部实际材质赋值，打包列表里有图片不说明它仍被使用。程序化虹膜可以避免像素化，但新增细节属于设计，眼形、虹膜比例与表情仍需对照原图。鼻尖提示和嘴线还须检查侧面，避免小球或粗线形成新的凸刺。

## 5. 头发与材质

先建立发际线、刘海轮廓、头顶和后脑体积，再分主发束和小发束。检查根部朝向、层间遮挡、尖端粗细及鬓角连接；重复等宽发束容易产生均匀条带感。

头发可用曲线、实体发束或发片，按风格及性能需求选择。静态发片检查背面、透明排序和斜角轮廓。需要模拟时再规划根部约束、碰撞和必要简化。

原画 UV 投射可以帮助颜色对齐，但其内置光影会掩盖错误曲面。至少保留一组中性材质、隐藏头发的脸部观察。眼睛等低分辨率裁图不能通过放大恢复原本不存在的细节。

按可见问题选择结构修复，不把某个角色的发束数量、分缝或参数当通用模板：

| 可见问题 | 优先检查与修复 | 复核方式 |
|---|---|---|
| 帽沿、齐平断根 | 整个发束截面是否埋入头顶壳体；按半厚度留出空间，连接发旋与侧后发根 | 正、侧、背及去纹理头发；只抬中心线可能仍穿壳 |
| 额前直线与颞部露皮三角 | 刘海下层遮挡、鬓角根部覆盖；下层边缘随主束错落 | 近景和斜侧面；不要降低整圈直帽沿遮住缺口 |
| 宽叶片、帘状后发、重复钩尾 | 参考中的主束走向、宽度变化、长短层次、空隙及左右差异 | 先少量主束核对正侧背体积，再加伴随细束；随机长度和更多等宽线不能代替设计 |
| 正面有长发，侧面体积不足 | 后脑至发尾的纵深随高度变化，内外层遮挡 | 固定侧面相机；同步变形发束、描边和高光几何，避免细节浮离 |
| 猫耳正面硬三角、侧面薄片 | 耳窝厚度和朝向；旋转后重新核对耳根外扩与整体轮廓 | 正侧面一起看；内耳与毛簇随最终耳壳表面贴合 |
| 耳毛像重复白片 | 连续毛簇本体、方向和轮廓，再补细毛尖 | 近景、侧面；耳壳变动后重新贴合，投射无命中须诊断，不能任意补深度 |
| 发夹像圆杆、呆毛侧面消失 | 薄片挤出和适量倒角、曲线纵深 | 对照配饰截面及两个视角；参考含绘画调整时记录三维折中 |

静态插画复刻中，如何选择程序材质或原画局部 UV、保留柔光与腮红、排查白底与层间露色，见 [静态插画质感与遮挡诊断](static-illustration-finish.md)。

发根穿插、轮廓和留白修好后，再设计局部高光带与遮挡阴影。纵向噪声不等于参考中的发丝组织。检查发束有意层叠与异常穿出，不把多层发型宣称为完全无自交或可打印实体。

## 6. 全身与动画扩展

本节提供按用途扩展的工作指导。当前公开包未附全身和动画的端到端验证案例，不据此宣称绑定、动画或目标引擎兼容性已经验证。

完整人物任务中，先建立身高比例、躯干、四肢、手脚和姿态，再制作服装及配饰；参考平面和肩领片不算人体。服装检查厚度、层次及与身体的交叠。真实尺度、UV 布局、贴图规格、网格预算和导出格式按目标平台决定。

有动画需求时进行适合变形的拓扑整理、骨骼、权重和表情设置。至少测试颈部转动、肩肘膝弯曲，以及请求中的眨眼、视线和口部动作；检查形变后穿插。导出需求必须实际导出并回读或在目标工具验证，不仅确认文件存在。

打印用途单独验证封闭性、壁厚等要求；实时角色的发片边界和打印实体不能共用同一个“全部通过”判断。

## 7. 三类验收证据

| 类别 | 检查证据 | 不能由此推断 |
|---|---|---|
| 外形 | 固定相机实际渲染、轮廓、五官比例、灰模和斜侧面观察 | 少数关键点接近不代表整体相似 |
| 工程 | 文件重开、依赖可用、坐标有限、退化面、异常边、法线及必要的交叠检查 | 网格检查通过不代表人物好看或水密 |
| 用途 | 静态多角度展示、指定动作、目标格式回读等实际测试 | 静态检查通过不代表动画、打印、所有引擎均可用 |

指标报告记录：参考及版本、相机、画幅、测量区域、样本数量、配准假设、原始网格/修改器求值网格/最终渲染的测量对象。

轮廓应测最终渲染或修改器求值结果；基准顶点或中心剖面可用于诊断，但不能替代可见轮廓。少量人工拟合点可能直接来自建模约束，接近零误差只说明约束实现。保留其他视角、未参与拟合的轮廓区域和整体视觉观察，避免把拟合误差当独立验收。

即使少量人工样本的像素误差很小，且有限网格检查通过，整体轮廓、风格和人物身份仍可能不符合参考。不要把此类数字设成通用相似度阈值；没有公开、可复核的评估数据时，不宣称量化还原精度。

## 8. 迭代、交付和中止

每轮先写最主要的可见问题，再改对应结构，渲染相同视角，对比改善与退化。核心问题持续不变时，重新检查相机、输入一致性及几何方法，必要时回到粗形或更换模板；不要把版本数量当成进展。

维护当前请求的待修项及保留约束，区分“已实施”“已目视复核”“工程检查通过”和“用户认可外形”。用户要求继续完成其他问题时，不因一项修好就结束；用户后续要求局部调整，也不代表其已认可此前全部相似度。检查应与改动成比例：独立去颈只需验证删除、保留对象和相关视图，无需重建整个角色。

最终从明确版本保存工程并打包所需纹理，重新打开检查。对外说明当前范围、实际完成项、已做验证及剩余缺口。建议使用“草模”“修形检查点”“静态交付”“动画验证通过”等准确状态，不以文件名 `final` 或 `restored` 作为成功依据。

用户叫停或清理时停止制作。清理前检查仍在运行的相关任务和打开工程；只处理授权范围，优先可恢复移动并记录原路径，验证项目残留。保留的渲染、日志及脚本是历史证据，文档要说明原生工程是否仍存在。
